# Generated Article normalization regex was designed from one example, not real data

The `legalSourceAnalysisCache` table's `markdownContent` (Generated Article content) is known to contain a letter-spacing artifact (e.g. "D E C I S I O N" instead of "DECISION"), most likely introduced by Tier 2 of `LegalSourceCacheSvc.analyze()` in `ilovelawyer-api`, which copies the external `documents` table's `formatted_markdown` into the cache with no cleaning step. We wanted to validate the normalization regex against real corrupted rows before writing it, but the local Postgres instance had no rows in `legalSourceAnalysisCache` at all (empty table), and no staging/prod database was available to inspect during this session. We chose to proceed anyway rather than block the fix indefinitely, designing the regex conservatively from the single known example (collapsing runs of 4+ single-space-separated single characters). To bound the risk of an unvalidated, lossy text transform running against real content, the backfill script (`scripts/normalize-generated-articles.ts` in `ilovelawyer-api`) defaults to a dry-run mode that prints a before/after diff per row instead of writing, requiring an explicit flag to commit changes. The regex should be re-evaluated against real data the first time it's run somewhere those rows actually exist.
