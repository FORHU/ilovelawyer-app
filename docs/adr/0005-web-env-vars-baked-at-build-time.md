# Web env vars are written to a file before `docker build`, not passed to `docker run`

`ilovelawyer-api`'s deploy workflows write a `.env` file on the runner and mount/pass it to `docker run` on EC2 at container start — its secrets (`DATABASE_URL`, `ACCESS_TOKEN_SECRET`, etc.) are read at Node process runtime, so this works. `ilovelawyer-app`'s two env vars (`NEXT_PUBLIC_API_URL`, `NEXT_PUBLIC_GOOGLE_CLIENT_ID`) are different: Next.js inlines any `NEXT_PUBLIC_*` value into the client JS bundle during `next build`, so by the time a container exists to `docker run`, the values are already baked into static files — passing them at runtime would have no effect on code already shipped to the browser. The deploy workflows (`deploy-production.yml`, `deploy-staging.yml`) instead write `apps/web/.env.production.local` on the GitHub Actions runner immediately before `docker build`, so the Dockerfile's builder-stage `COPY . .` carries the file in before `pnpm run build` (`next build`) runs. The file is never copied to EC2 and the deployed container receives no env file at all. If this app ever adds a genuinely server-only (non-`NEXT_PUBLIC_`) secret, that one *would* need the API's runtime pattern — the two mechanisms can coexist, but `NEXT_PUBLIC_*` values specifically must stay on the build-time path.
